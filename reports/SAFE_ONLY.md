## ⚠️ 度量口径更正记录（2026-08-22，共三轮，以本节为准）

这个项目的"真实回撤"数字前后改过三次。为避免再被误读，**本节的表格是唯一有效版本**，
下文正文里任何与之冲突的数字都以本节为准。

### 三轮的经过

1. **初版**：用 freqtrade 的 `*_wallet.feather` 快照重建净值曲线。事后证明，
   这个方法对**纯幸存币**的运行是准的，只对含已下架币的运行失真（因为该导出
   在币种价格数据中断后不再写行，持仓价值被永久漏记）。当时的判断基本正确。
2. **第二轮（过度纠正）**：发现零持仓日有 4,464 USDT 缺口后，判定整个方法作废，
   改写为订单流重建。但新实现有 bug——`reindex(days, fill_value=0)` 只填充缺失
   的日期行，对"该币当天无成交、但别的币有成交"的单元格留下 `NaN`，`cumsum`
   把 NaN 一路带下去，导致持仓价值在这些日子被随机丢弃。实测某天凭空少了 1,929
   USDT，制造出一个 19% 的幻影悬崖。**当时发布的 25.80% / 19.22% 等数字全部作废。**
3. **第三轮（当前）**：改为 `.reindex(days).fillna(0.0)`，并把浮点残渣阈值从
   1e-12 放宽到 1e-6（大额币种如 FUN 以千万枚为单位成交，收盘后残留约 1e-9 的
   尘埃会被一直按市价标记）。

### 当前有效数字（双重校验通过）

校验方式：① 重建末值 vs freqtrade 自报 `final_balance`；② **零持仓日**（账户
理应全是现金）重建值 vs「起始 + 累计已实现盈亏」。六次运行两项误差均在 20 USDT
以内（相对 1~2 万 USDT 账户约 0.1%）。

| 运行 | 报告收益 | freqtrade 回撤(已实现) | **真实回撤(盯市)** | Sharpe | 年化波动 |
|---|---:|---:|---:|---:|---:|
| X7 原版 · 120 幸存 | +142.31% | 2.63% | **4.59%** | 3.21 | 18.9% |
| Safe 修复 · 120 幸存 | +76.66% | 1.43% | **2.72%** | 3.05 | 12.7% |
| C 臂 · 80 幸存 | +191.00% | 3.78% | **3.73%** | 2.66 | 28.1% |

### 结论

- **Safe 版大幅降低回撤**：同一真实宇宙下 27.46% → 7.91%（降 71%）；同一 120 幸存
  宇宙下 4.59% → 2.72%（降 41%）。
- **生存偏差仍是最大的风险来源**：原版在纯幸存宇宙只有 3.73% 回撤，加入已下架币后
  暴涨到 27.46%（7 倍），Sharpe 从 2.66 掉到 0.60。
- **百分比 vs 固定仓位**：回撤 6.80% → 7.91%，收益 +90.83% → +145.10%，
  Sharpe 3.20 → 3.29。风险调整后仍是改善。
- 关于官方 CI 的 ≤15% 验收线：那条线定义在 freqtrade 的已实现口径上，与本表的
  盯市口径不是同一把尺子。按各自口径看，当前配置两边都在 15% 以内。

## 一、为什么弃用官方原版

逐行读完 `nfi_repo/NostalgiaForInfinityX7.py`（77,198 行）并做实证验证后，两个结构性
问题足以否决直接使用官方默认配置：

1. **默认无止损。** `stoploss=-0.99`、`system_v3_2_stops_enable=False`、
   `u_e_stops_enable=False`——官方默认配置下没有任何会主动止损离场的路径。
2. **收益依赖生存偏差。** `configs/blacklist-binance.json` 排除的 40 个交易对，
   今天 100% 已从币安现货下架——不是风险过滤器，是生存过滤器。三臂对照实验
   （见下）显示：把这些币放回同规模的真实宇宙后，原版收益从 +191%（对照组）
   掉到 +19.12%（−90%），真实回撤从 3.73% 暴涨到 27.46%（7 倍），Sharpe 从 2.66 掉到 0.60。

`NostalgiaForInfinityX7Safe`（`user_data/strategies/NostalgiaForInfinityX7Safe.py`）
修复了止损开关未接线的 bug，加了 30 天时间止损，把 grinding 加仓预算收紧到首仓的
0.5 倍。

三臂对照：A 是已发布结果（120 幸存币）；C 是 A 的幸存者子集（用于控制"宇宙变小"本身

|---|---:|---:|---:|---:|---:|---:|---|
| A 已发布（120 幸存） | 101 | 323 | +142.31% | 2.63% | +142.46% | 真实 **4.59%** | 通过 |

**为什么以前测不出来**：`IPairList._whitelist_for_active_markets()` 会丢弃
`market_is_active()` 为假的交易对，币安下架后仍在 exchangeInfo 里返回这些符号但标记
为非活跃——已下架币被**静默**移出白名单，freqtrade 只打一行 INFO 日志然后用更小的
宇宙继续跑，报告里毫无痕迹。你无法意外地回测到一个已经死掉的币。

**怎么绕过去**：`scripts/fetch_delisted_data.py` 从 `data.binance.vision` 恢复了 40 个
已下架币的历史 5m/15m/1h/4h/1d 数据（40/40 成功，38 个下架日期落在回测窗口内）；
`scripts/ft_delisted.py` 只 patch `market_is_active` 这一个判定点、只对这 40 个符号
放行，并拒绝在 `backtesting`/`download-data` 之外运行。

**关于此前记录的"数据质量问题"**：早期版本说"只影响生存偏差实验、不影响日常
回测"——这个判断**基本是对的**（`*_wallet.feather` 法对纯幸存币运行确实准确）。
中途有一版把它全盘推翻并换了新方法，但新方法自身有 NaN 传播 bug，反而产生了更大的
错误数字。完整三轮经过见文首「度量口径更正记录」。

## 五、X7Safe 修复了什么

```python
class NostalgiaForInfinityX7Safe(NostalgiaForInfinityX7):
    system_v3_2_stops_enable = True          # 旧版缺这一行，下面的阈值从未生效
    system_v3_2_stop_threshold_doom_spot = 0.08
    system_v3_max_stake = 0.5                 # 唯一被真正读取的 max_stake
    time_stop_enable = True
    time_stop_days = 30                       # 新增：切僵尸仓
```

旧版的实质性 bug：把 `system_v3_2_stop_threshold_doom_spot` 从 0.12 收紧到 0.08，
但没有同时设 `system_v3_2_stops_enable = True`。由于当前生效的正是 v3_2 分支
（`system_name_use = system_v3_2_name`），这个收紧后的阈值**从未参与过任何判断**：

```python
# NostalgiaForInfinityX7.py (long_exit_stoploss)
if is_system_v3_2:
    if self.system_v3_2_stops_enable and (profit_stake < -(entry_cost * 0.08)):
        return True, stoploss_doom
# 但旧配置里 system_v3_2_stops_enable = False  ← 整个条件被 and False 短路
```

旁证：旧 Safe 版的逐笔明细里，亏损的还是 COTI / CRV / RAD **同样 3 笔**，持仓天数
完全一致（537.1 / 382.4 / 3.7 天），订单数只因固定仓位小幅减少（745→652，169→165）。
持仓行为和原版几乎一模一样，正是因为风控没生效。

另外三个 `*_max_stake` 覆盖（`grinding_v1` / `grinding_v2` / `system_v3_1`）也都落在
死分支上（当前只有 `system_v3_max_stake` 被真正读取），已删除。

## 六、如果考虑实盘，五条不可协商的前置条件

1. **只做现货，不碰合约。** 无止损 + 杠杆是灾难剧本（参见社区 GitHub Issue #681：
   用户在极端行情下几乎爆仓）。
2. **`stoploss_on_exchange: true`。** 把最终防线放在交易所侧，不依赖 bot 存活和 API 延迟。
3. **放弃 `unlimited`，用固定 `stake_amount`。** unlimited 意味着账户越大单笔越大、
   全额复利。
4. **`tradable_balance_ratio` ≤ 0.85。** 给同时触发的 grinding 留出现金缓冲。
5. **把黑名单当成活的运维任务，不是配置。** 黑名单是当前唯一有效的尾部风险控制，
   而它只在**比市场更早知道哪个币要死**的时候有效；官方黑名单的更新滞后于事件。

## 六之二、仓位规模：固定金额 vs 百分比（已实现，2026-08-22）

背景：`stake_amount: 1500` 是锚定在 `dry_run_wallet: 10000` 这个回测起点算出来的
（1500/10000 = 15%）。如果实际本金不是 $10,000，这个固定数字就失去了意义——本金
$2,000 的话，一个槽位几乎押上四分之三身家；本金 $50,000 的话，单笔仓位又小得可以
忽略不计。

**槽位数：先降到 3，后改回 4（两次决定，原因如下）**

第一次决定（已过时，见下修正）：把 `max_open_trades` 从 4 降到 3，理由是"本金较小时，
槽位少一点，每个槽位分到的钱多一点，能避开交易所最小下单量"。**这个理由只在固定
金额模式下成立**——当时还没确定切到百分比仓位。

**修正**：切到百分比模式（见下）之后，每笔仓位大小是"账户总净值 × 15%"，**这个
比例和同时开几个槽位无关**——不管开 3 个还是 4 个槽位，单笔仓位金额都固定是
15%，槽位数只决定同时能开几笔、以及一次性最多部署多少比例的资金（4 槽 = 最多
60% 同时在场），不影响单笔仓位是否够大、是否会撞上交易所最小下单量。

真正决定"grinding 最细一档（首仓 5%）会不会撞上交易所最小下单额"的，只有
**账户总额**和**15% 这个比例**两个数字，与槽位数无关：

| 账户 | 15% 首仓 | 最小 5% 加仓档 | 状态 |
|---|---:|---:|---|
| $700 | $105 | $5.25 | 贴着下限，多数币种会被强制放大摊薄档位 |
| $1,000 | $150 | $7.50 | 部分币种（下限 $10 的）会被强制放大 |
| $2,000 | $300 | $15.00 | 安全 |
| $3,000 | $450 | $22.50 | 安全 |
| $5,000 | $750 | $37.50 | 安全 |

分界线大概在 $1,500~2,000——过这条线，机制正常运行；没过，机制依然能跑（自动
把阶梯按比例放大顶到下限），只是摊薄档位变粗，不算"坏了"。

**最终决定：槽位数改回 4**（2026-08-22，已落地）。既然槽位数不再影响单笔大小，
"3 个够不够"变成了纯粹的分散度问题——3 个槽位意味着最多同时持有 3 个不相关的币，
如果这几个恰好同涨同跌，集中度风险比持有 4~5 个要高。既然增加槽位在百分比模式下
不会牺牲任何单笔仓位大小，4 个槽位换来更好的分散度是免费的。

**已确认参数并实现**：`stake_amount` 从固定金额换成"账户总净值的一个百分比 +
一个绝对金额上限"，让仓位随真实本金等比例缩放，而不是绑死在 $10,000 这个回测基准上。

- **基准比例：15%**（=原固定 1500/10000 的隐含比例）。账户恰好等于 $10,000 时，
  行为与已验证的回测**完全一致**，偏差只来自"是否复利"这一个变量。
- **绝对上限：$4,500**（基准金额的 3 倍）。账户涨到约 3 万美元后封顶、不再跟涨。
- **计算基准**：`Trade.total_open_trades_stakes() + wallets.get_free(stake_currency)`
  ——现金 + 全部持仓的入场成本（不含未实现盈亏的逐笔重估值，因为该回调没有低成本
  拿到每个持仓当前市价的途径；差异只在持仓仍偏离入场价的这段时间内存在，不影响
  两种模式之间的切换逻辑）。
- **实现方式**：`NostalgiaForInfinityX7Safe.custom_stake_amount()` 里的
  `stake_sizing_mode` 开关（`"percent"` / `"fixed"`），计算出的百分比金额作为
  `proposed_stake` 传给 `super().custom_stake_amount()`，复用上游原有的各模式
  仓位系数（rebuy 0.25x、rapid 0.75x、grind 阶梯等），只替换基数来源，不改动
  模式判断逻辑本身。
- **grinding 预算联动**：`system_v3_max_stake`（加仓预算，当前 0.5 倍首仓）本身
  是相对首仓的比例，首仓换成百分比后自动跟着缩放，未额外改动。
- **验证**：短窗口冒烟测试（$10,000 起始资金）里，首仓实际下单金额为
  $1,499.9999 ≈ $1,500，与固定金额模式完全一致，确认切换点对齐无误。

**已在真实宇宙数据上完整对比（2026-08-22）**：把当前配置（百分比 15% + $4,500 上限 +
4 槽位）放进和第 08 节 B 组完全一样的真实宇宙（80 幸存 + 40 已下架）跑满 18 个月：

| 运行 | 笔数 | 亏损 | 报告收益 | freqtrade回撤 | **真实回撤** | Sharpe |
|---|---:|---:|---:|---:|---:|---:|
| X7 原版 · 真实宇宙 | 213 | 6 | +19.12% | 23.62% | **27.46%** | 0.60 |
| Safe · 真实宇宙（固定 $1,500，旧仓位） | 436 | 29 | +90.74% | 7.13% | **6.80%** | 3.20 |
| **Safe · 真实宇宙（百分比 15%+$4,500 上限，当前）** | 436 | 29 | **+144.96%** | 4.74% | **7.91%** | **3.29** |

百分比模式真实回撤略高于固定模式（7.91% vs 6.80%，复利放大了敞口），但收益高得多
